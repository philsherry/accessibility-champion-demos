- [x] **Track down intermittent test failures under full `npm test` runs** — a real, reproducible reliability gap, not incidental flakiness. Verified with 4 consecutive clean full `npm test` runs (635 passed / 0 failed each time), plus `npm run lint`.
  - **Fixed**: `tests/service-worker.spec.ts` was racing all 3 Mobile/Tablet/Desktop *projects'* full-site precache bursts against the one dev `http-server` at once (worse once `admin.html`/`receipt.html` grew `PRECACHE_URLS`). Restricted the whole file to the `Desktop` project only via `test.skip()` in `beforeEach` (service worker behaviour isn't viewport-dependent).
  - **Fixed — the real root cause of the SW test's own remaining failure**: `waitForPrecache()`'s use of `page.waitForFunction()` with an async predicate (reads the Cache API, itself async) intermittently returned after a single "not ready yet" evaluation instead of continuing to poll — reproduced deterministically running the SW spec alone with zero contention (no other projects, `workers: 1`), so this was never actually the contention bug it looked like from inside a full run. Confirmed by instrumenting the predicate and the service worker's install/activate/precache steps directly: the promise resolved while the cache was still empty, on both default `'raf'` polling and an explicit numeric `polling` interval — so the fix isn't a polling-mode tweak, it's not using `waitForFunction` for this predicate at all. Replaced with a plain `evaluate`-then-`sleep` loop driven from Node, which doesn't exhibit the problem (8/8 clean runs in isolation before rolling out).
  - **Also fixed**: `playwright.config.ts` had `fullyParallel: true` with no explicit `workers` cap, letting all 3 projects' tests hit the single dev `http-server` at once. Added `workers: process.env.CI ? 2 : 4` (machine has 10 cores, confirmed via `sysctl -n hw.ncpu` — the earlier "6 cores" note was a stale/incorrect reading). This addressed the separately-observed intermittent failures in `footer-site.spec.ts` and `responsive-layout.spec.ts` (not reproduced again across the 4 verification runs).
  - **Also cleaned up** (from an earlier pass): 3 orphaned `http-server` processes from ad-hoc debug servers, left running for over an hour and adding to dev-server contention. Killed by specifically-verified PID, not a broad `pkill`.

This was already true of the colour-coding *before* this change; the icon work inherits the existing gap rather than introducing a new one. The `@supports` guard means real visitors always get a fully functional plain-text `<select>` regardless — the enhancement activates automatically, no further code changes, whenever a browser ships default support. New test (`tests/components/admin.spec.ts`) verifies via `getComputedStyle()`/DOM structure against the one environment where this is actually checkable today.
- [ ] **Toast notification pattern review** — the "Add to cart" toast on `index.html` (bottom-centre, fixed position, `addToCart()` in `assets/js/index.js`) can disappear before a user notices it, and a screen magnifier user zoomed in elsewhere on the page can miss it entirely regardless of position. Screen reader users are already covered independently via the `#cart-status` live region — the toast is supplementary feedback for sighted users only.
